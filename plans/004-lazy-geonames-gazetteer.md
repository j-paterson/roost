## Why this matters

`dist/main.js` is 5.7MB, and ~4.3MB of that is an offline GeoNames gazetteer
(`packages/core/src/data/geonames-cities.json`: 68,350 city entries + 78,405
name keys) used only by the Places features. The data is *statically imported*
at `lib/geonames.ts:14`, which is reached from the plugin entry at startup:
`main.ts:15` (`import "./views/pipeline-views"`) → `places-map.ts:10` →
`geonames.ts`. Obsidian loads and evaluates plugin `main.js` synchronously at
every app launch, so every Roost user pays the multi-megabyte JSON parse and
permanent heap residency (~tens of MB once materialized into JS objects) on
every Obsidian start — including users who never open Places.

The bundle *size* is a known, accepted trade-off (geonames.ts's own header:
"Covers ~77% of our TikTok POI corpus on top of a ~4MB bundle cost"). This
plan does NOT shrink the bundle; it defers the parse so startup cost and
baseline memory drop to near zero for non-Places use, with no behavior change.

```ts
// geonames.ts:14-32
import data from "@/data/geonames-cities.json";

type Coord = [number, number];
interface GeoNamesData {
  version: string;
  cities: Record<string, Coord>;
  byName: Record<string, Coord>;
  gidToIso: Record<string, string>;
}

// JSON shape is correct at runtime but TS infers literal `cities` keys that
// don't statically narrow to Record<string, Coord>. Cast through unknown so
// the assertion is permitted.
const DATA = data as unknown as GeoNamesData;

export function countryGidToIso(countryGid: string | undefined | null): string | null {
  if (!countryGid) return null;
  return DATA.gidToIso[String(countryGid)] ?? null;
}
```

(The other two functions read `DATA.cities` / `DATA.byName` the same way —

## Steps

### Step 1: Ambient type for `*.json?raw` imports

Create `packages/core/src/types/raw-json.d.ts`:

```ts
// Vite `?raw` suffix imports the file contents as a string.
declare module "*.json?raw" {
  const content: string;
  export default content;
}
```

(`tsconfig.json` already includes `packages/core/src/**/*.d.ts`.)

**Verify**: `npm run typecheck` → exit 0

### Step 2: Make geonames.ts parse lazily

Replace the eager import + `DATA` constant with a `?raw` import and a
memoized getter. Target shape (keep the existing header comment and the three
exported function signatures EXACTLY as they are):

```ts
import raw from "@/data/geonames-cities.json?raw";

type Coord = [number, number];
interface GeoNamesData { /* unchanged */ }

let cached: GeoNamesData | null = null;
function getData(): GeoNamesData {
  if (!cached) cached = JSON.parse(raw) as GeoNamesData;
  return cached;
}

/** Test-only hook — whether the gazetteer has been parsed yet. */
export function __gazetteerLoadedForTests(): boolean {
  return cached !== null;
}
```

Then replace every `DATA.` read inside the three functions with `getData().`
(four read sites: `gidToIso`, `cities`, `byName` ×2). Delete the old
`const DATA = data as unknown as GeoNamesData;` line and the now-stale cast
comment above it.

**Verify**: `npm run typecheck` → exit 0, and
`grep -n '"@/data/geonames-cities.json"' packages/core/src/lib/geonames.ts`
→ no matches (only the `?raw` variant remains)

### Step 3: Tests

Create `packages/core/src/lib/__tests__/geonames.test.ts`. vitest runs tests
within a file sequentially, and module state persists across tests in the
file — the laziness assertion must come first, in the same `it` as the
first lookup:

```ts
import { describe, it, expect } from "vitest";
import {
  resolveByCityName,
  resolveGeoNames,
  countryGidToIso,
  __gazetteerLoadedForTests,
} from "@/lib/geonames";

describe("geonames lazy gazetteer", () => {
  it("does not parse the gazetteer at import time, then parses on first lookup", () => {
    expect(__gazetteerLoadedForTests()).toBe(false);   // import was free
    expect(resolveByCityName("london", "GB")).toEqual([51.509, -0.126]);
    expect(__gazetteerLoadedForTests()).toBe(true);    // parsed on demand
  });

  it("resolves by name case-insensitively via resolveGeoNames name fallback", () => {
    // no cityCode hit, falls through to byName lookup — requires a countryGid
    // that maps to GB; if countryGidToIso("x") returns null the function
    // returns null, so test the byName path through resolveByCityName instead
    // and keep resolveGeoNames coverage to the null path:
    expect(resolveGeoNames("nonexistent-code", null, null, null)).toBeNull();
  });

  it("countryGidToIso returns null for unknown/empty gids", () => {
    expect(countryGidToIso(null)).toBeNull();
    expect(countryGidToIso("not-a-real-gid")).toBeNull();
  });
});
```

(`resolveByCityName("london", "GB")` → `[51.509, -0.126]` was verified
against the real JSON at planning time.)

**Verify**: `npx vitest run packages/core/src/lib/__tests__/geonames.test.ts` → 3 pass

## Maintenance notes

- Follow-up explicitly deferred: defer `leaflet`/`motion`/`radix-ui` module
  init the same way (dynamic `import()` at first Places/map open). That's a
  larger change because Vite lib-mode inlines dynamic imports; measure before
  attempting. The gazetteer was the dominant cost (~75% of bundle bytes).
- If `scripts/build-geonames.mjs` regenerates a bigger dataset, the lazy
  boundary keeps startup flat — but first-lookup latency grows; if Places
  ever becomes a startup-visible view, consider warming `getData()` in an
  `onLayoutReady` idle callback instead of reverting to eager import.
- Reviewer focus: no remaining module-scope reads of `DATA`/`getData()` in
  geonames.ts (laziness is only as good as the absence of top-level calls).
